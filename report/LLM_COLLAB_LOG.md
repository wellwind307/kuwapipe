## 阶段一 · 算法可行性与软硬件划分

### 节点 1：卡通化能否用纯组合逻辑实现

- **背景**：拿到 golden 参考 `style_reference.py`（含中值、Kuwahara、gamma、饱和度、量化、线稿引擎），要决定哪些算子能纯组合、哪些必须用时序资源，以及软件实现哪里最慢。
- **提示词**（大意）：「卡通·无描边 + AWB 固定 256 这一配置，能否用纯组合逻辑实现？删掉空间滤波画面会怎样？软件实现哪部分最耗时？」
- **模型回答要点**：不能纯组合——3×3 中值需 2 行缓冲、Kuwahara 7×7 需 6 行缓冲 + 列累加寄存器，空间滤波本质是时序元件（结构限制，非面积问题）；点操作（gamma LUT、饱和度、posterize）可纯组合；删滤波会退化为「带噪点的色调分离」；软件最耗时是 Kuwahara（float64 + 积分图 + 大量临时数组，内存带宽瓶颈）。
- **采纳与纠错**：采纳。据此确立「空间滤波必须上硬件、点操作可上硬件」的软硬划分。
- **产出**：软硬划分依据；Kuwahara 最终下沉到 FPGA 的决策源头。

### 节点 2：灰度中值 → 彩色中值，手写 RTL 上板失败后改用官方 IP

- **背景**：教程官方中值 IP 是灰度版（内部 RGB→灰度→中值→灰度→RGB，输出 R=G=B 黑白），需要彩色。
- **提示词**（大意）：「官方中值 IP 输出是黑白的，怎么改成彩色中值？」
- **模型回答要点**：彩色中值 = R/G/B 三通道各自取中值（做 3 次）；先手写 `median9.v`（9 点排序，5 级流水）+ `video_median_color.v`（行缓冲 + 3×3 窗口 + 边缘复制），xsim 对拍 numpy 期望 0 失配。
- **采纳与纠错**：**否决手写版**。手写模块上板实测失败——它用「时钟域」valid 跟踪，行间消隐气泡会导致 valid 与数据错位；这是「仿真通过但上板失败」的典型。改用官方 Vitis Vision 彩色中值 HLS IP（`median_blur_color_0`）。
- **产出**：`median_blur_color_0`（HLS）；教训：帧/行边界与消隐气泡的处理，上板可靠性优先于仿真正确性，优先用官方验证过的 IP。

## 阶段二 · 视频通路接口与时序

### 节点 3：带时钟延迟的处理模块能不能加

- **背景**：用户在 camerain / hdmiout 处插自己的处理模块：组合逻辑正常，一旦引入时钟延迟就花屏。
- **提示词**（原文）：「这个工程在 camerain 和 hdmiout 处是不是不能另加带 clk 延迟的处理模块？我尝试过很多次，但凡不是组合逻辑，图像就会出问题。」
- **模型回答要点**：用**反证法**——这两条通路本就存在大量带延迟的模块（color_convert、axis_register_slice、pixel_pack/unpack、v_vid_in_axi4s、v_axi4s_vid_out 等），所以「不能加延迟」不成立。真正要求是**数据与同步标志（TUSER/TLAST/TVALID）同拍对齐**：组合逻辑 0 延迟天然对齐，时序逻辑只延迟数据不延迟同步就会错位。
- **采纳与纠错**：采纳。「数据与同步信号同拍」成为后续所有 RTL 的硬约束。
- **产出**：信号对齐原则（沉淀进技能包）；直接指导 video_style / kuwahara 等模块的控制信号延迟设计。

### 节点 4：卡通化 RTL 时序收敛（sat / median9）

- **背景**：`median3 → gamma → sat → posterize` 逐位对拍 golden 通过，但综合时序违例。
- **提示词**（大意）：「sat 级 WNS=-0.955ns、median9 串行排序 WNS=-15.386ns，怎么修？」
- **模型回答要点**：sat 拆两级流水（亮度计算一级、饱和度乘加一级）；median9 从串行选择排序（36 级依赖）改为奇偶转置并行排序网络，再拆 3 段流水（每段约 3 个比较级）+ 窗口打拍，共 4 级。
- **采纳与纠错**：采纳。收敛后时序转正。过程说明「功能 bit-exact 的模块综合后仍可能因组合路径过长爆时序」。
- **产出**：`sat.sv`、`median9` 流水化；教训「图像核的组合逻辑必须打够流水」。

### 节点 5：越权改动与撤回（重要自我纠错）

- **背景**：用户要求「输出几十帧后切回直通」，模型擅自扩大改动范围。
- **提示词**（原文）：「我没让你改你就不应该动。」
- **模型回答要点**：（此前动作）擅自给 video_style 增加运行时 enable 端口 + AXI GPIO 并重建 BD。
- **采纳与纠错**：**撤回**——恢复 ENABLE 编译期参数、删除 GPIO、重建 BD。确立「先确认方案→再动手」的协作纪律。
- **产出**：协作纪律；写入技能包「失效条件/坑」。

## 阶段三 · 集成与接口对接

### 节点 6：直通都不亮 → interface 展开失败

- **背景**：卡通算法仿真正确、直通是纯导线，但上板连直通模式都不显示。
- **提示词**（大意）：「算法做得再烂，直通也该正常；直通不正常，怀疑是模块与工程的融合问题。」
- **模型回答要点**：排查发现 `connect_bd_intf_net` 连 interface pin 时 interface **展开失败**——只连了 interface pin，signal pin（tdata/tkeep/tstrb/tlast/tuser/tvalid/tready）全部悬空，数据通路完全断开。
- **采纳与纠错**：采纳。手动逐个连接 signal pin（绕过 interface 展开）修复。教训：**接口对接优先于算法**——模块插不进通路，算法再对也没用；连完 interface 必须检查 signal pin 是否真正展开。
- **产出**：BD 对接检查方法论（沉淀进技能包）；这是「最值得记录的一条经验」。

## 阶段四 · Kuwahara 硬件实现与按键切换

### 节点 7：整数判别式与浮点 golden 逐位一致

- **背景**：把 Kuwahara(r=3) 做成 RTL，且要与 float64 参考逐位一致。
- **提示词**（大意）：「怎么让整数 RTL 和 float64 参考的 Kuwahara 逐位一致？」
- **模型回答要点**：用 `disc = 16·ΣY² − (ΣY)²` 替代浮点方差——两者只差正常数因子 2^20，`argmin(disc) ≡ argmin(var)`；Σ 项 ≤ 2^41 ≪ 2^53，float64 无舍入误差；均值用 `q + ((rem>8)|(rem==8&q[0]))` 精确等价 `np.round` 的银行家舍入。
- **采纳与纠错**：采纳。内部像素 0 LSB 差异。
- **产出**：`kuwahara.v` 核心 + `verify_kuwahara.py`；沉淀为技能 S3（bit-exact-golden）。

### 节点 8：流式协议三坑（TLAST / skid / flush）

- **背景**：xsim 自校验暴露三类流协议问题。
- **提示词**（大意）：「自校验 flag_err 不干净，帮我定位。」
- **模型回答要点与纠错**：① TLAST 应是**行尾**而非帧尾（否则下游 pixel_pack 无法分帧）；② 输出纯组合时，输入气泡 + 下游 ready 会让下游重复采样同一像素 → 加一级 **skid 寄存器**（out_vld 被取走后清零）；③ 帧末 flush 拍数不足丢最后 2 像素 → 扩展行改为 `LW=W+8`（3 拍右边界 + 5 拍排空）。
- **采纳与纠错**：全部采纳，`captured=384000/384000, mismatch=0`。
- **产出**：`video_kuwahara.v` 的 skid/flush 设计；对应技能 S1 的反压/协议经验。

### 节点 9：4 重错位重影 → 行宽硬编码 800（本次最关键）

- **背景**：第一版比特流上板出现约 4 重错位重影，但全尺寸 800×480 密集流仿真 384000/384000 逐位通过。
- **提示词**（大意）：「上板出现约 4 重错位重影，仿真却是 bit-exact 的，为什么？」
- **模型回答要点**：先确认 RTL 逻辑无误（仿真过），转而查上游——发现 HLS 中值 IP 的行列循环是**硬编码常量**（`icmp_ln204 == 10'd800`），每行固定输出 800 像素；而 PYNQ 的 `VideoMode(640,480)` 只写 VDMA/VTC 寄存器、不写该 IP 的 rows/cols。按 640 做行缓存 → 每行多 160 像素 → 行缓存「一行」≈0.8 条真实行 → 5 个虚拟行走完 4 条真实行 → 4 重影。
- **采纳与纠错**：采纳，把模块与 BD 参数改为 W=800/H=480 并重验。**人机协作关键点：用户上板反馈「4 重影」这一现象是定位起点**——没有这个板级反馈，纯靠仿真永远发现不了。
- **产出**：修正 W=800；沉淀为技能 S4（hls-ip-geometry：几何以源码常量为准，不信上层配置）。

### 节点 10：Vivado BD 三坑 + 跨时钟域约束

- **背景**：加按键切换时在 BD 集成与约束上连续踩坑。
- **提示词**（大意）：「module_ref 加端口后 BD 里不出现新端口；跨层次信号连不上；CDC 报违例。」
- **模型回答要点与纠错**：① Vivado 缓存 module_ref 旧端口表 → 换新模块名（`video_style_bypass`）重建；② 手动 `create_bd_pin` 两头连报「sink already connected」→ 改 `connect_bd_net` 跨层次直连（BD 自动生成边界引脚）；③ 准静态 `mode` 信号跨 100MHz→142.9MHz 被当普通路径优化 → 加 `(* ASYNC_REG="TRUE" *)` + `set_false_path`；④ 一次文本替换把 XDC 两行合并导致引脚约束丢失 → 恢复换行。
- **采纳与纠错**：全部采纳，`validate_bd_design rc=0`，新逻辑不在任何违规路径上。
- **产出**：`video_mode_switch.v`、`video_style_bypass.v`、`base.xdc`；对应技能 S2（vivado-ip-swap）。

## 阶段五 · 版权合规与提交整理

### 节点 11：第三方 IP 许可排查

- **背景**：进入提交准备，需确认提交包能否包含收集来的 IP。
- **提示词**（大意）：「帮我把工程里所有用到的第三方 IP 列出来，逐个看许可。」
- **模型回答要点**：正点原子 `cmos_capture_data.v` 头部为「All rights reserved / 盗版必究」，属专有代码，放进参赛包即再分发、超出默示许可；Digilent `rgb2dvi/axi_dynclk` 为 MIT/BSD-3、Xilinx PYNQ 为 BSD-3，需保留声明；Kuwahara 是 1976 公开文献，无专利无版权。
- **采纳与纠错**：采纳。初版把 Vivado 生成的 AMD 版权头误当风险，核对后修正为「保留头 + 声明」。
- **产出**：`IP审查报告_kuwahara_btn.md`、`THIRD_PARTY_NOTICES.md`、`third_party/`。

### 节点 12：自研替换 + 逐拍等价性仿真（含消隐期差异）

- **背景**：正点原子采集 IP 无开源许可，需替换。
- **提示词**（大意）：「采集 IP 有版权问题，找现成替代还是自己写？怎么证明等价？」
- **模型回答要点**：自研 `ov5640_capture`（DVP 同步 + RGB565→RGB888 + 上电稳定计数），并写 TB **并排例化**原 IP 与自研模块、同激励逐拍 `!==` 比全部输出；PASS 条件写成「0 失配且比较拍数 > 阈值」。
- **采纳与纠错**：采纳。仿真抓到一处真实差异——原 IP **消隐期保持最后一个像素**、自研初版清零，被 TB 抓到后改为一致行为。最终 **91,063 拍 / 0 失配 / PASS**。
- **产出**：`ov5640_capture.v`、`tb_ov5640_capture.v`；沉淀为技能 S1（ip-equiv-cosim）。

### 节点 13：清理与合规表述

- **背景**：工程准备提交，需剔构建产物并写清许可与承诺书口径。
- **提示词**（大意）：「提交包要剔除哪些目录？许可声明和承诺书怎么写才不算虚假陈述？」
- **模型回答要点**：剔除 `base.runs/base.cache/base.hw/.Xil/*.log/*.jou` 等纯构建产物；`ipshared` 不能一刀切删（含 AMD/Digilent/PYNQ 生成源码），只删正点原子 `ipshared/949d/`；承诺书如实勾选「使用第三方 IP」并附清单，切忌写「全部原创」。
- **采纳与纠错**：采纳。初稿建议「删掉整个 ipshared 保持干净」被团队否掉（会导致工程无法再综合），改为仅删 949d。
- **产出**：`SUBMISSION_CHECKLIST.md`、`THIRD_PARTY_NOTICES.md`；最终提交树 `kuwapipe/`
  （提交说明后来并入 `README.md`「提交包说明」一节）。

## 协作反思

**大模型做得好的一面**
- 算法对拍：能严格对照 golden 逐位验证（内部 0 LSB），避免手算错误。
- 工程操作：自主定位工具链、跑 Vivado/Vitis HLS/xsim 批处理、读网表追数据通路，效率远高于人工。
- 快速迭代：HLS 重写、RTL 编码、时序修复（拆流水/排序网络化）都能独立完成并给出数据。

**大模型的局限（本项目最大的教训）**
- **容易在错误方向空转**：反复纠结算法、帧结构、keep/strb，却迟迟抓不住「直通都通不过 = 融合问题」这个根本。
- **越权扩大改动**：曾擅自加运行时开关，被用户纠正后撤回。
- **「我觉得」多、「抓数据」少**：直到最后才回到「对照实验 + 仿真/抓信号验证」的正确排查法。
- **长会话变杂**：上下文太长会记忆混乱，需及时沉淀成文档。

**有效的人机协作方式（本项目总结）**
1. **先钉基线，再增量开发**：先确认「无处理的直通能显示」，再往上加图像处理。
2. **接口/融合优先于算法**：模块插不进通路，算法再对也没用。
3. **用仿真/抓信号验证，不靠猜**：每个结论都要有数据支撑。
4. **板级反馈不可替代**：「4 重影」「直通不亮」这类现象只有人上板才能发现，是定位深坑的起点。
5. **及时沉淀**：关键结论写进文档/技能包，避免长会话记忆丢失。
